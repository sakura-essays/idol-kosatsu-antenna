# 編集と保守

## 候補→審査→登録
`config/candidates.json` に `url`, `discovered_at`, `reason`, `status: pending` を記録。候補があるだけでは収集しない。元サイト・利用条件・公開フィード・筆者の表示名を確認し `sources.json` に一意のIDで追加。公開フィードが存在することは包括的な転載許諾を意味しない。本サイトはメタデータとリンクのみを掲載する。

未知の書き手を検索エンジンから無断自動取得する仕組みはない。検索は領域と年代を変えて手動で行い、候補を残す。活動終了グループ・地方・海外非韓国と、まだ掲載の少ない書き手を優先する。

## 記事を承認
RSSは記事単位の自動判定を行い、根拠不足の場合のみ確認待ちにする。手動確認の場合は、元記事でタイトル・筆者・日付・考察または感想を確認したら `moderation.json` の `articles` にURLをキーとして指定する。既存の13記事を入力例として参照。

必須は `status: published`, `verified_nonfiction: true`, `reviewed_title`（現在の題名と完全一致）, `reviewed_at`, `category_ids`。`group_ids`, `topic_ids`, `member_ids`, `song_ids` を適切に指定する。巧拙・独創性の採点は不要。編集時にタイトルが変わると再審査になる。未来日・未確認日付は公開しない。

RSS外は `manual_articles.json` に記事メタデータと `verified_at`, `verification` を追加し、上記と同じ方法で承認。公開日が日付しか分からない場合はYYYY-MM-DDのまま保持し、架空の時刻を補わない。

## 取り下げ・誤分類
`moderation.json` の `blocked_urls` に対象の正規URLを追加。筆者単位は `blocked_authors`。承認済み・手動登録・再取得・ピックアップより停止が優先される。
分類訂正は同ファイルの該当記事のID配列を修正。`python scripts/build.py` 後にコミットすると自動公開。

## 分類の考え方
大分類は組織所属のリアルタイム保証でなく、記事発見用の文化的な棚。IDは表示名と独立し、改名・旧称はaliases。人物と楽曲はグループIDへ関連付ける。同名人物は別IDで登録し、手動で記事に指定する。卒業・移籍は人物のaffiliationsに所属期間を追加し、過去の記事の所属を現所属で塗り替えない。自動提案はタイトルのグループ名を先に照合し、人物だけからグループを断定しない。辞書にない対象も大分類を指定して掲載可能。

## ピックアップ
`pickups.json` は空で開始。本文読了後、`url`, `note`（1〜160字）, `reviewed_at`, `criteria`（具体的な観察や解釈上の選定理由）を登録。公開停止・保留は表示対象外。反応数やAI採点は使わない。時期・領域・書き手の偏りを見直し、同じ記事の交換だけで済ませない。

## 取得失敗
`state/status.json` に直近の成否と最終成功日時。HTTP 304は成功。robots不許可、429、5xx、空フィード、25秒タイムアウト、4MB超は既存記事を保持し次回実行まで待つ。大量再試行しない。state/reviewは公開ビルドへ含めないが、GitHubリポジトリ自体は公開なので私的メモや個人情報を記録しない。

## 規模
公開データはメタデータ一括読込、検索対象文字列は初回に一度正規化、DOMは30件ずつ。書き手ページ生成は筆者別バケットを使い全件走査の繰返しを避ける。3万件のフィルタと交互表示をNodeで検証する（実スマホ速度の保証ではない）。数万件で転送量・初期パースが問題になったらWeb Workerと分割JSONに移行する。未検証の上限性能を保証しない。


## 公開日と体験日（第2段階）
元データの公開日時は元の値のまま保持し、表示日と公開年代はAsia/Tokyoに換算する。日付単位で確認した過去記事はYYYY-MM-DDを保持する。タイトル中の公演日、回想の対象年、執筆した年を公開日に置き換えない。例：2019年のラストライブ回想を2025年に加筆公開した記事は2025年に分類する。

noteの記事URLは共有・マガジン等のクエリを除去して正規化する。一方、WordPress等の `?p=123` のような記事識別パラメーターは保持する。

## GitHub接続に書込権限がない場合の保存
2026-11-17時点では接続書込が403だった（2026-11-18の本改修ではGit Treesで書込可能）。書込不可の場合は、所有者ログイン済みのGitHub画面から、変更済みソースだけをリポジトリ相対パスの `source-checkpoint.zip` としてルートへアップロードできる。`.git` や認証情報は含めない。`.github/workflows` はZIPに入れず、更新時のstate/distも含めない（最新蓄積を上書きしない）。

その後、既存のActionsを手動実行すると、ZIP展開→テスト→RSS取得→ビルド→通常ファイルのコミット→ZIP削除→Pages公開を行う。この経路は初回に動作確認済み。操作後は必ず最新のmain・Actions結果・公開記事数を確認して進捗を更新する。利用者にGitHub権限拡張を求めることを既定にしない。


グループ名・別名に検索語全体が完全一致する場合は分類IDで照合し、IVEとLIVE等の混同を防ぐ。その他の自由語は部分一致のまま。大分類ごとのグループ候補には、記事の複数分類を通じて関連するグループも含める。

## 自動掲載（2026-11-18）
収集時に `publication.py` がRSS本文から根拠を抽出し、本文を保存せず `rss_evidence` に結果・分類・長さ・ハッシュ・取得日時を保存する。`decision` は最終結果、human/automatic/block、理由、判定日時、ルール版を記録。読者向けデータには含めない。有料API不要。抽出ルール（EVIDENCE_VERSION）または辞書変更時は条件付き取得を解除して根拠を再取得する。最終判定ルール（VERSION）だけの変更は保存済みの根拠から再判定する。

`config/sources.json` の `publication_mode` は eligible / standard（新規の既定） / cautious / stopped。いずれも記事単位の関連性・創作判定を通す。standard は一般的な題名や混在日記を保留し、eligible は本文の強い主題根拠があればこの追加保留を解除できる。cautious はタイトルにも主題と考察・感想の形式を要求。自動昇格は行わない。旧 article_policy は履歴として残すが新しい判定では publication_mode を使う。

`config/publication.json` の enabled=false で自動公開のみ停止できる。手動判断は独立して維持。自動非掲載は削除ではなく state/articles.json に記録する。復活は moderation.json に通常の確認済み承認を書く。

初回移行時点の全URLを backlog_urls に固定。過去記事は判定が published でも released_urls に入れるまで確認待ち。新着は同じ記事判定を通って自動公開。`python scripts/rejudge.py` でドライラン結果・無作為20件ずつ（固定シード）・書き手別/グループ別の候補件数を出す。元記事を照合し、検証したURLを released_urls に追加して段階移行する。件数上限が毎回動いて公開記事が入れ替わる方式ではない。

`state/review.json` は本当の不明記事と未移行過去記事だけ。`state/publication-dry-run.json` は運営用の候補報告。分類辞書の未収録、一般語、複数グループが本文だけに現れる場合、40字未満のRSS、宣伝と感想の混在は保留し得る。長さは文章力の採点ではなく判定情報の下限。

## 2026-11-18登録の30人：新着だけ安全に自動公開
`publication_mode: manual` は明示的な手動確認指定として引き続き利用可能。今回追加された30人はRSS・初期の掲載記事を確認できたため `standard` に変更し、同時に `auto_publish_after: 2026-11-18T13:20:00+09:00` を指定した。**公開日時と最初の収集日時が両方ともこの境界より後**であり、通常のRSS内容判定で掲載条件を満たした記事だけ自動公開する。日時の不明・日付のみ・旧記事の再取得は保留する。

境界以前の記事は、初回収集が遅れても一括自動公開されない。手動承認済み記事はそのまま掲載し、確認待ち記事も勝手に承認しない。対象の30人だけが切り替え対象で、他の書き手のモードや段階移行設定は変更しない。記事の取り下げには従来通り `moderation.json` を使う。新規登録の既定は `standard` だが、過去記事の一括流入を避ける必要がある書き手には `auto_publish_after` の設定を推奨する。
